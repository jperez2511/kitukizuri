# DashLite forms

## Canonical examples

Inspect these before implementing form UI:

```text
src/resources/views/krud/edit.blade.php
src/resources/views/krud/components/input.blade.php
src/resources/views/krud/components/select.blade.php
src/resources/views/krud/components/select2.blade.php
src/resources/views/krud/components/textarea.blade.php
src/resources/views/krud/components/password.blade.php
src/resources/views/krud/components/daterange.blade.php
```

Also inspect neighboring feature views when the requested form is not Krud-based.

## Basic field structure

The current Krud input component uses the DashLite form hierarchy:

```html
<div class="form-group mb-3">
    <div class="form-control-wrap">
        <label class="form-label-outlined">Label</label>
        <input class="form-control form-control-outlined">
    </div>
</div>
```

This is more authoritative than a generic Bootstrap `mb-3` + `form-label` sample when working within the same UI family.

## Outlined controls

Current text-style Krud inputs default to:

```text
form-control
form-control-outlined
form-label-outlined
form-control-wrap
```

Do not mix outlined label positioning with unrelated markup without checking how the relevant SCSS expects the DOM to be structured.

## Grid placement

Krud fields expose column classes and are typically placed inside Bootstrap rows.

Typical field-level wrappers use:

```text
col-md-6
```

or another responsive grid class.

Do not use fixed widths when the grid already handles the desired responsive behavior.

## Selects

Standard selects use Bootstrap-compatible classes such as:

```text
form-select
```

Select2 fields currently use:

```text
form-select js-select2
```

and are initialized in the component's scripts.

Before adding another Select2 initializer, check whether the component or `NioApp.select2` already initializes the target.

## Select2 runtime

`src/resources/js/init.js` defines `NioApp.select2` and supports data-driven options including concepts such as:

- placeholder,
- clear,
- search,
- width,
- theme,
- UI modifier,
- RTL direction.

The current Krud Select2 Blade component also performs direct jQuery initialization.

When changing Select2 behavior, inspect both places and avoid double initialization.

## Validation feedback

The Krud input component displays Laravel validation messages beneath the control using a danger text class.

When implementing new reusable form components:

- preserve Laravel's validation message behavior,
- associate labels with controls,
- preserve `name`/`id` semantics,
- maintain existing error-state conventions in neighboring components.

## Dynamic components

`src/resources/views/krud/edit.blade.php` uses `<x-dynamic-component>` to render field definitions generated by the Krud system.

If the task concerns a Krud-generated form, do not bypass that field schema by hardcoding inputs into the view unless the task explicitly requires a one-off section outside the dynamic field system.

## Dependencies between fields

Krud edit logic supports dependent fields and existing JavaScript for showing/hiding dependent controls.

Before adding a second conditional-field mechanism, inspect the existing dependency structure and determine whether the request can be represented through the current field configuration.

## File inputs

The JavaScript runtime includes `NioApp.BS.fileinput` behavior for displaying selected file names.

Krud also has handling for its own file-related field types.

Search current field implementations before adding another custom file chooser script.

## Buttons and actions

Form actions commonly use existing button classes such as:

```text
btn
btn-space
btn-success
btn-danger
```

Use semantic button types and preserve submission state/disabled behavior where existing code already handles async saving.

## Custom form CSS

Do not override `.form-control`, `.form-select`, `.form-label-outlined`, or `.form-control-wrap` globally for a single feature.

If a specific form needs custom composition:

```text
.feature-name .form-control { ... }
```

is safer than a global rewrite, but first check whether a DashLite modifier or Bootstrap utility solves the need.

## Form implementation checklist

Before finishing:

- Existing field components were inspected.
- Label/control association is correct.
- Responsive grid behavior is preserved.
- Current outlined-control markup is respected where used.
- Select2 is not initialized twice.
- Bootstrap 5 syntax is used for related interactive elements.
- Validation feedback remains visible.
- Custom CSS is scoped.
- Dynamic Krud fields remain dynamic when applicable.
- Dark mode/theme state does not depend on hardcoded white backgrounds or fixed text colors.
